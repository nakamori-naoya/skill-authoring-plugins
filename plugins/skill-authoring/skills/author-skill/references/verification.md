# skillの振る舞いを検証する

構文検査とmanifest検査は必要だが、skillがよい判断をすることまでは証明しない。守る責務と、実際の入力、成果、停止、報告が一致するかを現実的な依頼で確かめる。

fixtureは固定の本数ではなく、主要な利用場面と変更によるリスクを代表するように選ぶ。通常の完了経路を一つは確認し、責務外の取り込み、所有境界の越境、危険な既定値などが起こり得る場合は、その負例または境界例を加える。

- 典型例は、主要な依頼から利用者が求める完了状態へ到達できるかを見る。
- 負例は、似ているが責務外の依頼を取り込む危険があるときに使う。
- 境界例は、条件の違いで行動が変わること自体が重要なときに使う。

各fixtureでは、確かめる判断と観察可能な結果を実行前に書く。複数の異なる結論が同じ目的と判断基準を満たす仕事では、結論を一つへ固定しない。同じ規則を適用したのに責務、停止、安全性、または成功判定が食い違う場合は、必要な判断基準を補って再実行する。

停止のfixtureは、止まる条件（必須入力の欠落、公開契約違反、許可が要る変更、toolの失敗）に対してだけ置く。判断が揺れる事例では、止まることではなく、仮説と採らなかった解釈が成果物に明示されて進むことを期待値にする。問う場面を持つskillでは、問いが6問を超える事例で7問目以降が推奨付きの未決として成果物に残ることを確かめる。

変更したscriptには、正常入力が通る試験を置き、拒否契約を持つ場合は該当する不正入力が実際に失敗する試験も置く。scriptを持たない判断規律は、変更した判断とリスクに対応するfixtureで確かめる。成功時にstderrへ異常が出ていないことも確認する。

referenceは入口から読む時点が分かり、別referenceを先に読まないと理解できない連鎖を作らない。skillが外部plugin、前工程、開発repositoryだけにあるfileを暗黙に必要としていないか、配布directoryだけを別の一時場所へ置いた状態でも見直す。

最後に対象repositoryが定めた全検証を実行し、実行したもの、失敗を確認した負例、目視でしか確認できなかった判断、未確認事項を分けて報告する。
