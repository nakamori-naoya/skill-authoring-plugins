# skillの振る舞いを検証する

構文検査とmanifest検査は必要だが、skillがよい判断をすることまでは証明しない。守る責務と、実際の入力、成果、停止、報告が一致するかを現実的な依頼で確かめる。

fixtureは固定の本数ではなく、主要な利用場面と変更によるリスクを代表するように選ぶ。通常の完了経路を一つは確認し、責務外の取り込み、所有境界の越境、危険な既定値などが起こり得る場合は、その負例または境界例を加える。

典型例は、主要な依頼から利用者が求める完了状態へ到達できるかを見る。負例は、似ているが責務外の依頼を取り込む危険があるときに使う。境界例は、条件の違いで行動が変わること自体が重要なときに使う。

各fixtureでは、確かめる判断と観察可能な結果を実行前に書く。複数の異なる結論が同じ目的と判断基準を満たす仕事では、結論を一つへ固定しない。同じ規則を適用したのに責務、停止、安全性、または成功判定が食い違う場合は、必要な判断基準を補って再実行する。

停止のfixtureは、skillが何を変えるかに合わせて置く。資料を作るskillでは、判断が揺れる事例で、止まることではなく、仮説と採らなかった解釈が成果物の未決に明示されて進むことを期待値にする。コード、外部の状態、他人の資料を変えるskillでは、曖昧な入力や想定外の値で止まり、何が分からないかと提案を返すことを期待値にする。どちらのskillでも、必須入力の欠落、公開契約違反、許可が要る変更、toolの失敗で止まることを確かめる。問う場面を持つskillでは、grillが返した未決（上限で問われなかった論点を含む）が推奨付きの未決として成果物に残ることを確かめる。

変更したscriptには、正常入力が通る試験を置き、拒否契約を持つ場合は該当する不正入力が実際に失敗する試験も置く。scriptを持たない判断規律は、変更した判断とリスクに対応するfixtureで確かめる。成功時にstderrへ異常が出ていないことも確認する。

判断の持ち主は、変更したskillが持つ判断ごとに、同じpackageと関係するpackageのskillを読んで確かめる。同じ判断を別の答えで書いているskillがあれば、どちらが持ち主かを決め、もう一方を参照へ書き換えるか、持ち主への変更提案として報告する。「対象外として返す」の返し先は、その入口が実在し、その判断を実際に持っていることを開いて確かめる。

skillが成果物の形を決めている箇所（template、雛形、記入例、出力の形式、報告の形式、PR本文の組み立て方）は、`write-doc` が公開の資料として宣言している「書くときの規範」（公開入口 `write-doc` の `references/writing-norms.md`）に照らして読む。中身の項目をそのまま箇条書きの欄や表の列にした雛形は、理由と判断を段落で書けない形を利用者に強いる。表は同じ属性を持つ三つ以上のものを行で比べる箇所に、箇条書きは因果の無い本当の並列と順序のある手順に残し、それ以外は見出しと段落で書く形に直す。表が適している箇所は残し、表を減らすこと自体を目的にしない。これは読んで判断することなので、検査scriptには入れない。

referenceは入口から読む時点が分かり、別referenceを先に読まないと理解できない連鎖を作らない。skillが外部plugin、前工程、開発repositoryだけにあるfileを暗黙に必要としていないか、配布directoryだけを別の一時場所へ置いた状態でも見直す。

最後に対象repositoryが定めた全検証を実行し、実行したもの、失敗を確認した負例、目視でしか確認できなかった判断、未確認事項を分けて報告する。
