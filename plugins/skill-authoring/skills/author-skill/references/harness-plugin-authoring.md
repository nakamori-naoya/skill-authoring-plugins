# harness pluginのskillを作成・更新する共通規律

この文書は、`harness-pluginsv2` workspaceに属するplugin repositoryでskillを作成・更新するときの意味上の正本である。workspaceの`.agents`、`.claude`、各plugin repositoryの`AGENTS.md`は、この規律を複製せず参照する。

この文書が所有するのはskillの責務、指示、resources、検証の判断規律である。marketplaceやmanifestのschema、公開・内部入口の配置、playbook契約、release、installなどworkspace固有の構造と運用は、workspaceのplugin package契約と各repositoryの規約が所有する。両方が適用される場合は、skillの意味と行動をこの文書で決め、その形がpackage契約に収まるように実装する。

## 守る価値から制約を決める

- 各制約は、守る利用者価値、公開契約、所有境界、安全性のいずれかを説明できるときだけ置く。
- ファイル数、行数、工程数、見出し数、例の数を品質の代理にしない。外部形式または独立した責務から結果として決まる個数だけを固定する。
- 一つのskillは、利用者が単独で完了させたい一つの仕事を、開始から検証・報告まで完了する。工程が多いことを分割理由にせず、取り除いても独立した価値を返す能力は別のskillまたはcomposition候補にする。
- 題材固有のdomain、役割名、データ構造、件数、保存先、実装方式を、全利用者への既定値にしない。

## 指示は判断と行動を完結させる

`SKILL.md`は内容として次を持つ。見出し名と個数は固定しない。

- 目的: 読み終えると何を完了できるか
- 入力契約: 必須入力、任意入力、入力が満たさない条件の扱い
- 判断基準: 観察対象、結論を分ける述語、そのときの行動
- 手順: 結果へ影響する順序と、各工程が返す状態
- 停止条件: 止まる条件と、仮説を明示して進む条件
- 出力契約: 成果物、報告、未決、検証結果

重要な条件を「適切に」「必要に応じて」「十分に」だけで終えない。何を観察し、どの違いで行動または成果が変わるかを書く。禁止が3つ以上並ぶなら、肯定形の判断基準または停止条件へ畳む。畳めない禁止には代わりに返せる結果を添える。

止まるのは、必須入力が無く成果が無意味または危険になる、公開契約に反する、外部変更に許可が要る、toolが失敗する、保存先を確認できない場合である。判断の揺れ、資料不足、複数解釈では止まらず、その時点で最も筋の良い仮説、根拠、採らなかった案を成果物へ明示して進む。根拠の無いことを事実として書かない。

利用者へ問う場面では、対話の作法をskillごとに複製しない。対話を担う公開入口へ、調べても分からず答えで成果が変わる問いだけを渡す。返った未決は推奨を仮置きして成果物へ明示し、同じ実行で再び問うのは利用者が求めた場合か、その決定なしでは停止条件に当たる場合だけにする。

## resourcesは利用条件で分ける

- `SKILL.md`は仕事全体の入口とし、主要な判断、手順、停止、報告を失わせない。
- `references/`には条件付きの詳細判断、利用時に全文読む契約、代表例を置く。入口から、いつ読むかを直接示す。
- `scripts/`には、閉じた入力とrepository内の正本から正誤が一意に決まり、同じ判定を反復する処理だけを置く。
- `assets/`には成果物として再利用するtemplateや素材を置く。将来用placeholder、同じ規律の複製、同期blockを置かない。

公開入口と内部skillは、配布directory内の`SKILL.md`、`references/`、`scripts/`、`assets/`と、宣言した公開依存だけで仕事を完了できるようにする。開発repositoryだけにあるfile、兄弟skillの内部path、実行済み状態、暗黙の順序へ依存しない。

toolを使うskillは、入口directory基準の相対path、入力、出力、失敗の観測方法、失敗時に止まるか回復するかを一か所で宣言する。root解決用環境変数、設定展開script、マクロ、解決済み設定を読む指示をagent向け本文へ持ち込まない。

## 機械検査と意味評価を分ける

scriptへ入れるのは、次のすべてを満たす規則だけである。

1. 判定に必要な閉じた入力を列挙できる。
2. 期待値を導くrepository内の正本がある。
3. 正規化後の入力へ判定が一意である。
4. 合格集合と拒否集合を真偽述語で書ける。
5. 違反箇所を修正可能な診断として返せる。
6. 正例、反例、境界例をfixtureまたはself-testにできる。

構文、schema、識別子、配置、参照の実在、宣言の対応は機械検査にできる。責務分割、命名、文章、設計、例、未決、トレードオフ、複数資料の意味整合はagentが対象を読んで評価する。キーワード数、文長、見出し数、類似度、LLM採点を意味評価の代理gateにしない。

新しい検査を追加する前に、正本、入力、正規化、合格述語、失敗時の診断、正例、反例、境界例、意味評価として残す範囲を宣言する。この宣言を書けなければscriptへ追加しない。

## repositoryの規約と合成する

対象pathへ適用される`AGENTS.md`、`CLAUDE.md`、`.agents`、`.claude`と、repository固有の検証入口を先に読む。この共通規律はrepository固有の公開契約、配置、命名、保存先を上書きしない。衝突があれば、両方を満たす形を探し、両立しなければ変更せず衝突箇所を返す。

既存skillでは発見名、呼び出し方、配布境界、version方針を保ち、依頼に必要な箇所だけを変える。新規skillで対象repositoryに構造規約が無ければ、公開入口一つ、`SKILL.md`一つを最小の入口とし、必要なresourceだけを追加する。

変更後は、対象repositoryが定める全検証と、主要な利用場面、責務外を取り込む負例、結論が切り替わる境界例を確認する。構造検査の成功と意味上の妥当性を分けて報告する。

## 代表的な境界

- 典型例: 既存pluginの一つのskillへ判断基準を追加する。既存の責務と入力・出力を保ち、変更した判断を典型例と境界例で確かめる。
- 反例: 収集、要約、外部投稿、予定登録という独立成果を、同じ題材という理由だけで一つのskillへ詰める。利用者が単独で求める成果ごとに分け、順序はcompositionが所有する。
- 境界例: 表現に特定語が含まれるかは一意に検査できるが、その語が業務上妥当かは文脈で変わる。前者だけをscriptへ置き、後者はagentが根拠付きで評価する。
