# 曖昧さを排除する指示構造

skillの文章は説明ではなく、実行者が次の行動を決める規則である。異なる実行者が同じ入力から別の行動を正当化できるなら、その指示は未完成である。

skill全体は次の順に書く。対象repositoryが別の必須構造を定める場合だけ、その構造へ対応付ける。

1. 何であるか／何ではないか
2. 入力と開始条件
3. 番号付きworkflow
4. 成果と成功判定
5. 停止条件と停止時に返す内容

workflow内の各指示は次の四点を同じ箇所で特定する。

1. 適用条件: どの観察事実が揃ったときに使うか
2. 必須行動: 誰が何を読み、判断し、変更し、実行するか
3. 成功判定: 何を観察できれば次へ進めるか
4. 失敗時: 何を変更せず、どの理由と不足情報を返して停止するか

「適切に」「必要に応じて」「十分に」「可能なら」「など」「考慮する」「確認する」だけで行動を終えない。これらを使う場合は、直後に選択条件、対象、観察可能な完了を置く。たとえば「必要に応じてreferenceを読む」ではなく、「入力形式が既定以外なら、形式名と一致するreferenceを一つ読み、該当referenceがなければ形式を推測せず停止する」と書く。

代名詞と省略主語を避ける。「それ」「前のもの」「結果」を、指す成果物名またはfield名へ置き換える。`AまたはB`は選択条件を併記し、条件が重なる場合の優先順位を書く。否定条件は、禁止だけで終えず、代わりに返す結果を指定する。

一つの段落へ複数の命令を埋め込まない。順番が結果へ影響する命令は番号付きで並べ、並列なら順不同と明記する。分岐は「条件なら行動、そうでなければ行動」の両側を閉じる。期限、件数、path、formatの値を固定するのは、違反時に具体的な失敗が起きる場合に限る。

解釈の一致は、文章の厳しさではなく適用結果で確かめる。同じfixtureを二通りに読める箇所を探し、それぞれがどの語を根拠にしたかを特定する。語を強調して済ませず、分岐条件か停止条件を書き直す。利用者の決定がなければ条件を一意にできない場合は、推測せず、答えによって分岐が決まる一問を返す。
