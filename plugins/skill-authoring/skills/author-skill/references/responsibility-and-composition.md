# 責務と構成の境界を決める

skillは、利用者の依頼と対象だけで一つの仕事を完了させる。「何を受け取り、何を完了状態として返すか」を一文にしたとき、成果が別々の依頼でも単独で必要になるなら、同じskillへまとめない。

責務は肯定側だけで定めない。「これは何か」の直後に「これは何ではないか」を置く。非該当側には、名前や見た目が近いため誤って含めやすい仕事を書く。肯定例だけでなく非該当例を並べることで、どの違いが完了状態を変えるかを明示する。

工程が多いことは分割理由ではない。一つの成果へ至る発見、判断、変換、検査、保存は、一つのskillの内部workflowになりうる。一方、取り除いても残りが独立した価値を返す能力は、別のskill候補である。

同じ題材、利用者、技法、成果物fileを扱うだけでは、同じ責務にならない。次を比べる。

- 利用者が達成したい目的と、答えたい問い
- 受け取る入力と、返す完了状態
- 完了を判定する条件
- 途中で止める条件と、未決を返す相手

たとえば「具体例を一つの検査済みscenarioへ書き直す」ための観察と整形は一つのskillにできる。しかし、独立した複数skillを決まった順で実行することはskill authoringではなくcompositionである。順序を一つのskillへ隠さず、今回作る一つの能力と別作業の境界を返す。

skillにしない方がよい場合もある。一度限りの依頼にだけ通じるprompt、対象repositoryの保守規約、同じ入力から同じ出力を一意に算出できる製品codeは、再利用可能な判断能力としてのskillとは異なる。名前を付けて配布する前に、skillがなければ繰り返し失われる非自明な判断があるかを確かめる。
