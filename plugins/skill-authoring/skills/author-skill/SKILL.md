# author-skill

これは、一つの再利用可能な仕事を単独で完了できるskillを作る能力である。読み終えると、依頼された仕事を一つの責務へ絞り、実行agentが判断と行動を選べる`SKILL.md`と必要な`references/`・`scripts/`を書き、対象repositoryの検証を通して報告できる。複数能力の順序、marketplace全体、対象domainの知識、repository規約を作る能力ではない。

## 入力

- 作成または更新したい仕事と、期待する完了状態
- 対象repositoryの絶対pathと、既存のplugin / skill source
- 利用者が明示した制約と、対象repositoryに既にある規約（AGENTS.md、CLAUDE.md、`.agents/rules/`など）
- `references`: 任意。追加で従う資料の絶対path配列。手順の最初に読む。プロジェクト固有の規約や文脈は、対象repositoryのAGENTS.md / CLAUDE.mdとこの入力で渡される

## 1. 対象と適用規約を確かめる

変更対象のrepositoryとskillを特定し、そのpathへ適用される指示書をすべて読む。既存plugin / skillから構造、命名、manifest、検証commandを調べる。規約がなければ`skills/<skill-name>/SKILL.md`を入口にし、条件付き詳細があるときだけ`references/`、反復する決定的処理があるときだけ`scripts/`を作る。対象repositoryまたは変更権限を特定できない場合は、不足情報を返して止まる。

## 2. 一つの責務へ絞る

[責務と構成の境界](references/responsibility-and-composition.md)を読み、利用者が単独で完了させたい仕事と、その仕事に含めない責務を明らかにする。独立利用できる成果が複数残る場合は、今回の対象と別作業を分ける。どれを今回扱うかが依頼から一意に決まらないときは、依頼の中心に最も近い一つを仮説として選んで進み、選ばなかった能力と選んだ理由を責務境界に明示して、確認は成果とともに求める。

## 3. 使用から意味を固定する

[意味と境界](references/meaning-and-boundaries.md)を読む。主要な利用場面と、責務を取り違えやすい場面を比べ、判断や行動を実際に変える概念だけを書く。境界が重要な場合は、判断が変わる条件を具体例で確かめる。特定事例の関心を普遍規則にせず、題材固有の値、役割名、件数、置き場を既定値にしない。

## 4. 判断と行動が伝わる指示を書く

[判断と行動を明確にする方法](references/instruction-clarity.md)を読む。`SKILL.md`は内容として、目的（読後に何ができるか）、入力契約、判断基準、手順、停止条件、出力契約を持つ。見出しの形や個数は固定せず、本文で揃っているかを確かめる。

判断基準は、条件が結果、安全性、または所有境界を変える箇所へ、観察対象と二者択一の述語を肯定形で書く。「〜しない」が3つ以上続く箇所は、観察対象を持つ判断基準か停止条件へ畳む。畳めない禁止には、代わりに返せる結果を添える。

基盤の配管は指示から外す。root解決の環境変数、設定展開script、「解決済みYAMLを読め」型の指示が残っている場合は、skillが実際に使うtoolを入口directory相対のpathで示し、入力、出力、失敗の観測方法、失敗時に止まるか回復するかを一か所に書いたtool契約へ置き換える。

複数の妥当な成果を許す仕事では、結果を一つへ固定せず、選択を支える基準を示す。

停止条件は二群に分けて書く。止まる条件にしてよいのは、必須入力の欠落で成果が無意味または危険になる、公開契約に反する入力を受けた、外部への変更に許可が要る、toolが失敗した、保存先を確認できない、のどれかに当たる場合だけである。判断の揺れ、資料の不足、複数の解釈は止まる条件にせず、その時点の根拠から最も筋の良い仮説を採り、仮説であることと根拠、採らなかった解釈を成果物の未決または該当箇所へ明示して進み、確認は成果物とともに求める手順にする。「推測せず一問で確認して止まる」「〜は受け付けない」「〜を成功の証拠にしない」型の文は、この二群のどちらかへ畳む。事実の捏造は許さず、根拠のないことを事実として書かせず、仮説は仮説と分かる形で書かせる。

作るskillが利用者へ問う場面を持つなら、対話は対話を担う公開入口（`grill`）へ委ね、その作法（問う数の上限、提示の仕方、合意の取り方）をSKILL.mdやreferenceへ書かない。skillが持つのは、答えで成果が変わる問いの選び方（調べれば分かることを問わない）、返った未決の推奨を仮置きして成果物へ反映すること、同じ実行で再び問う条件（利用者が求めた場合か、その決定なしでは止まる条件に当たる場合）だけである。author-skill自身の確認も同じ規律に従う。

## 5. repositoryへ適合させて実装する

[repositoryへの適合](references/repository-fit.md)を読む。descriptionには完了状態と主要な利用場面を書く。本文には仕事を完了する順序、重要な判断、必要な停止条件、報告を置く。条件付き詳細だけを直接到達できるreferenceへ分け、繰り返す決定的処理だけをscriptにする。入口から必要なresourceへ利用条件付きで到達でき、配布directory外の未宣言fileを必要としないことを確かめる。

## 6. 振る舞いを検証する

[検証](references/verification.md)を読み、主要な利用場面と変更のリスクを代表するfixtureで判断と停止を実行する。対象repositoryの全検証を実行する。構造検査は構文、識別子、配置、参照の実在だけを言う。判断基準が観察可能か、否定の連打が残っていないか、6要素が本文に揃っているか、停止条件が止まる条件と仮説を明示して進む条件に分かれ判断の揺れで止まる文が残っていないか、問う場面が作法をgrillへ委ね、問いの選び方と結果の扱いだけを持つかは、実行agentとして読んで判定し、文長やキーワードの数で代理しない。

## 7. 報告する

変更したskill、守る責務と主要な判断、resourcesを分けた理由、実行した検証とその結果、目視評価、未確認事項を簡潔に報告する。

## 停止条件

止まるのは次のときで、それ以外の判断の揺れでは止まらない。

- 対象repository、対象skill、変更権限を特定できず、書く場所が無い
- 更新対象が存在せず、推測で別のskillを変更することになる
- 対象repositoryの規約と依頼が両立せず、どちらかを破らなければ書けない
- 対象repositoryの検証commandが失敗し、直せない

止まるときは、不足している情報、両立しない規約と依頼の箇所、または失敗した検証とその出力を返す。

判断の揺れでは仮説を明示して進む。

- 独立した能力が複数残り、今回の対象が依頼から一意に決まらない: 依頼の中心に最も近い一つを選び、選ばなかった能力を責務境界へ書く
- 判断条件を具体例と反例で区別し切れず、解釈が複数残る: 主要な利用場面に合う解釈を採って判断基準と例を書き、採らなかった解釈を未確認事項へ書く
- 依頼が問う場面の扱いや停止の二群に触れていない: この本文の判断基準どおりに書き、報告でその判断を示す

仮説として置いた責務、判断基準、停止条件は、報告で仮説と分かる形で示し、確認は作成したskillとともに求める。

## 出力

- 作成または更新した自己完結skill
- 「何を受け取り、何を完了状態として返すか」という責務一文
- 「何であるか」と「何ではないか」を並べた責務境界
- 各判断の条件、必須行動、成功判定、止まる条件と仮説を明示して進む条件、停止時の返却
- 実行した典型例・負例・境界例の検証結果
- 未確認事項または停止理由
