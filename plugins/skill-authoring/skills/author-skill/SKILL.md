# author-skill

利用者が繰り返し頼む一つの仕事を、実行するエージェントが判断を外さずに済む skill にする。skill に書くのは、エージェントが自分では外しやすい判断の要だけである。考えれば分かる手順、言い換え、網羅のための列挙、防御の注記は書かない。書く前に、対象 repository の AGENTS.md と既存の skill を読み、配置、命名、manifest、検証の入口はそれに合わせる。

## skill にするか、どこで分けるか

名前を付けて配る前に、skill が無いと繰り返し失われる、自明でない判断があるかを確かめる。一度限りの依頼、repository の保守の決まり、同じ入力から同じ出力が一つに決まる処理は skill にしない。

分けるかどうかは、独立して要る成果が一つかで決める。工程が多いことは分ける理由にならない。一つの成果に至る調査、判断、変換、検査、保存は、一つの skill の中の流れでよい。反対に、取り除いても残りが単独で価値を返す能力は別の skill にする。独立した skill を決まった順で呼ぶ仕事は、一つの skill に隠さず、その境界を返す。

## 意味は、似て非なる例と反例と境界で決める

語や規則を一行の定義で終えると、エージェントは当てはまる場面を自分で広げる。主要な利用場面に加え、似ているが別の行動になる例、はっきりした反例、条件を一つ変えると結論が切り替わる境界を並べ、その差を生む条件を本文に書く。一つの案件で要った値や道具を、全員への規律にしない。その関心を取り除いても仕事が成り立つなら、skill には埋め込まず、判断例として添える。

## 一つの判断は一か所に置き、持ち主を参照する

書く前に、この skill が持つ判断を挙げ、同じ判断をほかの skill が既に持っていないかを読んで確かめる。持っていれば書き直さず、持ち主を名前で指す。二つの skill が同じ判断を別の答えで書くと、使う側はどちらかを黙って覆すしかなくなるからである。「対象外として返す」と書くなら、返し先の入口が実在し、その判断を実際に持っていることを開いて確かめる。

## 止まる基準は、その成果物にとって何が結論かで書く

止まるか進むかは、欠けた情報が成果物の結論を変えるかで決める。変えるなら止まって提案し、変えないなら仮説を明示して進む。skill の停止条件には、この基準を言い換えず、その skill の成果物にとって何が結論かだけを書く。たとえばドメインモデルでは集約の境界が結論で、図の配置は細部である。戻すのに他人の手が要るものを変える skill は、細部でも止まる。利用者へ問う場面は grill へ渡し、問いの選び方と、返った未決を成果物でどう扱うかだけを書く。

## 重みは理由で伝え、強調は一か所だけにする

エージェントは指示を文字どおりに読むので、太字や「必ず」「絶対」は規則の重みではなく適用範囲を広げる。規則の重みは、それが何を守るか（安全、公開の入出力、持ち主の境界、利用者の決定）を一文添えて伝える。強調を使うのは、読み落とすと取り返しがつかない一か所だけにし、理由を同じ文に書く。思考の量や途中の報告を文章で上げ下げしない。

## 業務の言葉で名付け、見出しと文章で書く

skill 名、概念、節の名前は、その仕事をする利用者が会話で使う言葉で付ける。作り手の仲間内でだけ通じる説明語や、何を指すか分からない権威の語を作らない。本文は、判断の大半を決める少数の要を先に書き、見出しと地の文で理由と因果を説明する。箇条書きは本当の並列と順序のある手順に、表は同じ属性を行で比べるときだけに使う。書き方の細部は write-doc の「書くときの規範」（公開入口 `write-doc` の `references/writing-norms.md`）に従う。

## references と scripts は使い方で分ける

SKILL.md は入口として、判断の要と止まる場面を失わせない。条件付きでだけ要る詳細は references に置き、いつ読むかを SKILL.md に書く。scripts に置くのは、閉じた入力から正誤が一つに決まる処理だけである。読んで解釈しないと決まらないことは script で判定せず、エージェントが読んで評価する。エージェントが自分で作った値を自分で照合する仕組みは作らない。

## 振る舞いで確かめて報告する

主要な利用場面の典型例、責務の外を取り込みそうな負例、結論が切り替わる境界例を用意し、それぞれで確かめる判断と観察できる結果を先に書いてから、書いた skill で試す。停止の例は、結論を変える欠落と細部だけの欠落を対にする。対象 repository の検証をすべて実行し、変えた skill、持つ判断、試した例と結果、採らなかった案、確かめられなかったことを報告する。

対象 repository、対象の skill、依頼の意図のどれかが分からず結論が変わるとき、repository の規約と依頼が両立しないとき、検証が落ちて直せないときは、書かずに止まり、分からない点と提案を返す。
