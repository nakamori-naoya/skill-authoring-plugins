# 振り分けの基準

記憶や規約の一件を、昇格、留める、破棄のどれにするかを決めるときに読む。

## 六つの問い

一件ごとに、次の六つの問いに答える。答えは資料に一文ずつ残し、どの問いの答えで振り分けが決まったかが読み手に分かるようにする。

1. 案件の固有の値（上限の数、製品名、framework名、置き場）を抜いて、一文の原則として言えるか。
2. その原則を、別の題材（業務知識の薄いCRUD中心のサービスなど）に当てても害が無いか。
3. 根拠はどこにあるか。技術上の理由か、外部の契約か、利用者の好みか。
4. 何回現れたか。一つの案件の中で繰り返されたか、複数の案件で現れたか。
5. 置くならどこか。pluginの規律の本文か、判断例か、案件の規約か。
6. それが無かったら、何が壊れたか。実際に起きた出来事で言えるか。

## 答えから振り分けへ

1と2に「はい」と答えられ、3の根拠が技術上の理由か外部の契約なら、昇格を提案する。4で一回しか現れていないなら、pluginの本文ではなく判断例として提案する。6で壊れたことを言えないなら、仮説として提案し、未決に書く。

3の根拠が利用者の好みか、案件だけの技術の選択なら、案件に留める。好みであっても、同じ利用者の他の案件でも繰り返すなら、利用者全体の指示（案件をまたぐ指示の置き場）へ移す提案を添える。

今の規約、コード、pluginのどれかと食い違っているなら、六つの問いに答える前に破棄を疑う。どちらが新しい決定かを、commitの日付や規約の文面から確かめ、古いほうを破棄の提案にする。どちらが新しいか確かめられないときは、仮説として未決に書く。

## 判断例（図書館の貸出）

図書館のsiteの案件で、記憶に「延滞の判定は返却期限の翌日0時から」とあった。1で原則にすると「業務の時刻の境界は資料が決め、実装は資料に従う」となり、2で別の題材に当てても害は無い。3の根拠は業務の資料にあり、技術上の理由ではない。ただし境界の値そのものは案件の業務知識なので、値は案件に留め、原則だけを、業務知識を実装へ写すpluginの判断例として提案する。

同じ記憶の索引には「延滞は返却期限の当日から」と書かれていた。索引と本文が食い違っているので、それ自体を所見として記録し、今の業務の資料と照らして、索引の行を破棄の提案にする。
