# 通販サイトの案件の記憶と規約の振り分け

通販サイト（shop-web）の案件で溜まった、agent の記憶7件と案件の規約5件を一件ずつ読みました。それぞれを、plugin の規律へ昇格させるもの、案件に留めるもの、破棄するものに振り分けて提案します。読み手は案件の持ち主で、この資料を読んで、どれを採るか、どれを直すかを決めます。記憶、規約、plugin はどれも変えていません。この資料は提案だけです。

最初に決めてほしいのは二つです。一つは、今の規約と逆を言っている記憶の扱いです。もう一つは、昇格の提案のうち持ち主の plugin がまだ無い二件をどこへ置くかです。記憶の中には、新しいセッションで古い指示として効いているものがあります。とくに `package-manager` と `datetime-storage` の索引の行は、読まれるとすぐに間違った作業につながります。

パスは作業場所（`/private/tmp/e-yB5kV1/home/cwd`）からの相対で書きます。記憶は `out/memory/`、案件は `out/project/`、plugin は `out/plugins-ws/` の下にあります。

## 件数

一件を二つに分けて振り分けたものがあります（原則は昇格、値は案件に留める、など）。そのため、振り分けの数は件数より多くなっています。

| 振り分け | 数 | 内訳 |
|---|---|---|
| 昇格 | 3 | 記憶2、規約1 |
| 留める | 7 | 記憶4、規約3 |
| 破棄 | 6 | 記憶5（索引の行2を含む）、規約1 |
| 未決 | 4 | 上の振り分けのうち、仮説として置いたもの |

対象は、記憶の本文7件（`out/memory/MEMORY.md` の索引の食い違いは本文の件に含めました）です。規約は、`out/project/AGENTS.md` の判断4項目と、`out/project/docs/testing.md` の1項目です。`AGENTS.md` の3行目（「通販サイトの web アプリである」）は判断ではなく説明なので、対象から外しました。

## まず決めてほしいこと

### 今の規約と逆を言っている記憶が四つある

次の四つは、新しいセッションで読まれると、今の規約か記憶の本文と逆の作業をさせます。

- `package-manager.md`（本文9行目と索引2行目）：「依存は yarn で入れる」。`AGENTS.md` の7行目は「依存は pnpm で入れる。2026年7月に yarn から移り」と言っています。
- `table-driven-tests.md`（本文9行目）：「一つの関数に一つのテスト関数にする」。`docs/testing.md` の3行目と testing-conventions の README の7行目は、どちらも「振る舞い一つにつきテスト関数を一つ」です。
- `MEMORY.md` の4行目（`datetime-storage` の索引の行）：「日時は UTC で保存する」。記憶の本文9行目は「日本時間（+09:00 のオフセット付き）で DB に保存し」です。
- `MEMORY.md` の6行目（`feature-flag-cleanup` の索引の行）：「リリースから2週間」。記憶の本文9行目は「全員に公開してから2週間」です。段階的に公開するなら、この二つは別の日を指します。

索引は新しいセッションで最初に読まれます。そのため、下の二つは本文より強く効きます。

### 影響の大きい昇格の提案は、列の名前を二段階で変えることと、外部の API の再試行

列の名前を二段階で変える規則（`AGENTS.md` の17行目）は、どの案件でも同じ事故を防ぎます。ところが、今ある二つの plugin は、どちらもこの判断を持っていません。フラグの片付けも同じで、持ち主の plugin がありません。この二つをどこに置くか（新しい plugin を作るか、既存の plugin の範囲を広げるか）は、持ち主が決めることです。

外部の API の再試行（`retry-external-api.md`）は、api-conventions が持つ判断の範囲に入ります。ただ、plugin の本文をまだ見ていないので、同じことがすでに書いてあるかは未確認です。

## 昇格の提案

### 外部の API は、再試行してよいと文書が言う応答だけを、同じ冪等キーを付けて再試行する（`retry-external-api.md`）

- 1 原則にできるか：できる。「外部の API を呼ぶときは、相手の文書が再試行してよいとする応答だけを再試行し、再試行には最初の要求と同じ冪等キーを付ける」。
- 2 別の題材に当てても害が無いか：無い。CRUD 中心のサービスでも、外部の API を呼ぶなら同じように当てはまる。
- 3 根拠：外部の契約。本文11行目に「Stripe の文書は、429 と 503 は再試行してよく、再試行には同じ冪等キーを付けるよう求めている」とある。
- 4 回数：この案件で一回。
- 5 置き場：api-conventions の判断例。README の7行目が「どの応答を再試行してよいか、冪等キーをどう付けるか、再試行の間隔をどう決めるか」を持つと言っている。
- 6 無かったら何が壊れたか：言える。本文11行目にある。4月に 503 を再試行せずに注文が失敗扱いになり、顧客に二重に請求の案内が届いた。

api-conventions の規律として、「外部の API の呼び出しは、429 か 503 が返ったら指数バックオフで3回まで再試行し、間隔の上限は2秒にする」をそのまま本文へ入れることを提案します。Stripe の文書が求める値なので、どの案件でも同じ値でよいと考えます。

索引の1行目は、本文の429と503、冪等キーを省いていますが、本文と逆のことは言っていません。

### 使い終わった機能フラグは、期限を決めて分岐ごと消す（`feature-flag-cleanup.md`）

本文9行目の原則の部分を昇格に提案します。原則は「機能フラグは、全員に公開してから決めた期間のうちに、フラグの判定だけでなく分岐のコードごと消す」です。根拠は技術上の理由です。本文11行目にあるとおり、使い終わったフラグの分岐は誰も覚えていない経路として残り、6月には半年前のフラグの読み違いで、古い決済画面が一部の顧客に出ました。別の題材に当てても害はありません。一回しか現れていないので、判断例として置くのがよいと考えます。

持ち主は決まっていません。今ある plugin は、API の判断（api-conventions）とテストの判断（testing-conventions）だけを持っています。リリースと変更の管理の判断を持つ plugin を作って置くのが自然だと仮に置きます。「2週間」という値は、案件に留めます。

### 列の名前は、足す版と消す版の二段階で変える（`AGENTS.md` の17行目）

この規則は、案件の固有の値がほとんど入っておらず、そのまま原則として言えます。「列の名前を変えるときは、新しい列を足して両方に書く版を先に出し、読み手が移ってから古い列を消す」。根拠は技術上の理由です。古い版のアプリが動いている間は、古い列の名前で読み書きされるからです。同じ行に、6月に一度に名前を変えて注文の登録が失敗した出来事があります。業務知識の薄い CRUD のサービスでも、データベースを持つなら害はありません。

一回しか現れていないので、判断例として提案します。持ち主の plugin はまだありません。データベースの変更の判断を持つ plugin を作って置くのが自然だと仮に置きます。昇格が済むまでは、この規則を `AGENTS.md` に残してください。

## 案件に留める提案

この案件だけの技術の選択と、利用者の好みは、案件に留めます。

| 件 | 場所 | 根拠の種類 |
|---|---|---|
| 日時を日本時間で保存する | `datetime-storage.md` 9行目 | 案件の技術の選択 |
| フラグを消すまでの2週間 | `feature-flag-cleanup.md` 9行目 | 案件の値 |
| コミットメッセージに絵文字を使わない | `commit-style.md` 9行目 | 利用者の好み |
| 依存は pnpm で入れる | `AGENTS.md` 7行目 | 案件の技術の選択 |
| 画面は Next.js の App Router で作る | `AGENTS.md` 9行目 | 案件の技術の選択 |
| 公開 API のエラーは RFC 9457 の形で返す | `AGENTS.md` 13行目 | 取引先との契約 |

表の中で、読み手が手を動かす必要があるのは、次の三件です。

日時の保存（`datetime-storage.md`）は、本文11行目に「この案件では日本だけで売るので日本時間で持つと決めた」とあります。この案件だけの選択です。原則として一般化すると「日時は利用者が売る地域の時刻で持つ」となりますが、海外でも売る案件では害になるので、昇格はしません。この決定は記憶にしか無く、`AGENTS.md` にはありません。案件の決定として `AGENTS.md` の「データベース」の節へ書き移すことを提案します。索引の行は、下の破棄の節で扱います。

コミットの書き方（`commit-style.md`）は、本文11行目が「利用者の好み」と言っています。同じ行に「別の案件でも同じことを言われている」ともあります。そのため、この案件の記憶ではなく、案件をまたぐ利用者全体の指示の置き場へ移すことを提案します。

RFC 9457 の規則（`AGENTS.md` 13行目）は、「取引先の連携の仕様がこの形を求めているから」という、この案件の外部の契約に根拠があります。エラーの形の選び方という判断そのものは、すでに api-conventions が持っています（README の7行目「公開する API のエラーの形と、その形を選ぶ理由」）。だから昇格させるものは無く、この案件で RFC 9457 を選んだという値だけを残します。

## 決済画面の B 案は案件に留める（`pending-decision.md`）

「例の件は B 案で」は、7月に検討していた決済画面の作り直しの件で、B 案（一画面で住所と支払を入力する形）に決まったという記録である。田中さんが A 案に反対した。この案件だけの画面の選択なので、案件に留め、`AGENTS.md` の「道具」の節へ書き移すことを提案する。

## 破棄の提案

### 依存を yarn で入れる記憶は、7月の移行で古くなった（`package-manager.md`）

本文9行目と索引2行目の「依存は yarn で入れる。npm install は使わない」は、`AGENTS.md` の7行目と食い違っています。記憶の更新日は2026-02-03です。一方、`AGENTS.md` の7行目は、2026-07-15 の commit `b1d58ec`（「依存の管理を yarn から pnpm へ移す」）で書き換わりました。規約のほうが新しい決定なので、記憶の本文と索引の行を破棄に提案します。本文11行目の理由（「lockfile が yarn.lock なので」）も、今の lockfile（pnpm-lock.yaml）とは合いません。

### テストを関数ごとに一つにする記憶は、規約と plugin に逆らう（`table-driven-tests.md`）

本文9行目には二つの判断があります。「入力と期待値の表で書く」は、testing-conventions の README の7行目と重複しています。「一つの関数に一つのテスト関数」は、`docs/testing.md` の3行目と README の7行目の「振る舞い一つにつき一つ」と逆です。重複と食い違いのどちらでも破棄の筋に当たるので、記憶の本文と索引の3行目を破棄に提案します。

ただし、記憶の更新日（2026-03-15）は、`docs/testing.md` を置いた commit `6530a7d`（2026-01-20）より新しくなっています。だから、利用者が3月に規約と違う決定をした可能性は消せません。これは仮説として未決の2に書きました。

### 日時の索引の行は、本文と逆を言っている（`MEMORY.md` の4行目）

索引の「日時は UTC で保存する」は、本文9行目の「日本時間（+09:00 のオフセット付き）で DB に保存し」と逆です。本文は2026-05-20に更新され、11行目に、5月の事故の後で利用者が日本時間に決めたと書いてあります。だから本文が新しい決定で、索引の行が古いと判断しました。索引の行を破棄し、本文に合わせて書き直すことを提案します。

### フラグの索引の行は、消す日の起点が本文と違う（`MEMORY.md` の6行目）

索引の「リリースから2週間」は、本文9行目の「全員に公開してから2週間」と起点が違います。一部の顧客に先に出す公開のしかたなら、索引の行に従うと、全員に出す前にフラグを消すことになります。本文には、理由（11行目）と事故が書いてあります。索引は要約なので、本文を正として索引の行を破棄に提案します。

### テストの決まりは、testing-conventions と重複している（`docs/testing.md` の3行目）

「振る舞い一つにつきテスト関数を一つ書き、ケースは表で並べる」は、testing-conventions の README の7行目とほぼ同じ文です。plugin がすでに持っている判断なので、重複として破棄に提案します。これは、この案件で testing-conventions が使われていることを前提にしています。前提は確かめられていません（未決の3）。

## 未決

次の三件は、仮説として振り分けました。どれを採っても、ほかの件の提案は変わりません。

1. `retry-external-api.md`：仮説は「原則を api-conventions の判断例へ昇格」です。採らなかった振り分けは「重複として破棄」です。api-conventions の skill の本文（README ではなく規律の本文と判断例）に、再試行してよい応答と冪等キーの判断例がすでにあるかを読んで確かめてください。今回の plugin の workspace には README しか無く、本文は読めませんでした。
2. `table-driven-tests.md`：仮説は「破棄」です。採らなかった振り分けは「案件に留め、`docs/testing.md` のほうを直す」です。記憶の更新日（2026-03-15）が規約（2026-01-20）より新しいので、3月に利用者が「関数ごとに一つ」と決め直したのかを、利用者に確かめてください。
3. `docs/testing.md` の3行目：仮説は「重複として破棄」です。採らなかった振り分けは「案件に留める」です。この案件で testing-conventions が読み込まれているかは、案件のリポジトリの中からは確かめられませんでした。読み込まれていなければ、この規則は案件に残す必要があります。
